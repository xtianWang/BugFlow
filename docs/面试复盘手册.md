# BugFlow Agent 实习面试复盘手册

## 三分钟介绍

我做了一个建立在 BugFlow Issue 管理后端上的 AI Debug Agent。原系统使用 FastAPI、
SQLAlchemy、Pydantic 和 JWT，已有用户、项目、成员、Issue、状态流转与 46 个测试。
我没有再搭一套认证系统，而是把 Agent 当作原业务的一种新入口。

用户先用自然语言查询项目和 Issue。Agent 通过真实 LLM tool calling 自行选择查询工具，
后端把工具调用绑定到当前用户和当前项目。模型没有数据库凭证，也不能指定其他用户身份。
如果需要排查代码，模型只能提出 Debug 任务。任务记录仓库别名和 commit，必须由项目 Owner
在另一个接口明确批准，才会进入队列。

执行阶段最重要的区分是：Git worktree 负责版本隔离，不负责安全隔离。我实现了独立 worker，
先检查 Linux Docker 和 runsc，再把过滤后的代码快照交给无网络、无宿主凭证、限制 CPU/内存/PID
的容器。模型只能读取文件、修改已有 app Python 文件和运行固定测试命令，不能提交任意 shell。
最后把基线结果、修复后测试和 Git Diff 交给用户审核。接受报告只记录决定，不自动应用补丁。

工程上我强调可观测、可拒绝和可验证：工具调用有 Trace，模型请求有超时和有限重试，任务有
状态机与原子领取。只有实际 Diff 与测试证据满足条件，后端才标记修复成功。
目前我验证了原业务回归、权限、状态机、真实 worktree 修改与清理，以及替身驱动的失败分支。
我还在本机 WSL2 Ubuntu 的 runsc 中完成了真实模型修复验收：加法误写为减法，基线失败、修复通过、
真实 Diff、Owner 授权与报告审核。它只是一个小型可重复案例，不代表所有真实 Bug 都能自动修好。

## 完整链路

JWT -> get_current_user -> 项目权限 -> 查询 Agent loop -> LLM tool call -> 参数校验 ->
真实业务查询 -> tool observation -> 下一轮模型决策 -> request_debug -> 待授权 ->
Owner 审核 commit -> queued -> worker 原子领取 -> 再校验权限/绑定 -> 沙箱能力检查 ->
worktree -> 基线 pytest -> 读代码/修改 -> pytest -> Diff -> 报告 -> Owner 接受或拒绝。

## 必须解释清楚的设计取舍

- 原业务权限复用：查询允许 Owner/Member；Debug 执行批准和结果审核只允许 Owner。
- 仓库绑定采用运维配置白名单，API 不接受路径。牺牲自助绑定便利，减少 V1 攻击面。
- 模型提出行动，后端判定能否行动；prompt 不是安全边界，工具集合和权限校验才是。
- worktree 不执行 checkout filter；仅从 Git blob 提取允许的普通文本文件，拒绝符号链接。
- 单次 worker + 数据库状态适合演示；还不是有恢复能力的分布式任务系统。
- 只改已有 app/*.py，不改测试，不提供 shell；限制通用性以便理解和验证执行边界。
- 不把所有 pytest 通过等同于修复一定正确，仍需要人工看 Diff 和测试覆盖。

## 18 个追问

1. **这是真 Agent 还是关键词分支？**
   生产使用 HTTPS tool calling；模型返回工具名和参数，loop 执行并回传 observation，最多 8 轮查询或 10 轮 Debug。
2. **为什么没用大型 Agent 框架？**
   V1 工具数量有限，显式 Python 循环更容易审查权限、预算和异常；不是所有 Agent 都需要框架。
3. **JWT 和权限的区别？**
   JWT 验证身份，数据库查询确认用户活跃；项目 Owner/Member 规则决定其可访问哪些资源。
4. **项目里真有通用 RBAC 系统吗？**
   没有通用角色表或策略引擎。实际是基于 owner_id 与 ProjectMember 的项目级角色权限，面试不能夸大。
5. **模型能自己批准吗？**
   不能。批准不是工具；独立 JWT API 检查 Owner、明确布尔授权和精确 revision。
6. **怎么防跨项目查询？**
   project_id 由 API 绑定，工具不接受任意项目参数；get_issue 同时校验 Issue.project_id。
7. **仓库怎么授权？**
   运维登记 alias -> project_id + 绝对 Git 根目录，模型只使用 alias，后端拒绝不匹配映射。
8. **为什么 worktree 不够？**
   它隔离文件版本，但普通进程仍可读取主机文件或访问网络。代码测试必须放进真正受限运行时。
9. **容器是否绝对安全？**
   不是。实现要求 runsc、最小挂载、无网络、非 root 和资源限制，还依赖可信运维与更新后的运行时。
10. **如何防 prompt injection？**
    将 Issue/文件视为数据，模型没有审批/任意命令能力，工具还做权限与路径检查。不能承诺模型完全不被诱导。
11. **如何判断成功？**
    基线 pytest exit 1，改后 exit 0，且有真实非空 Diff；只表示在现有测试下验证，不证明语义绝对正确。
12. **为什么禁止修改测试？**
    防止模型通过删断言制造通过；代价是 V1 不能生成回归测试，需要后续独立审查流程。
13. **发生模型错误怎么办？**
    超时/传输/429/5xx 有最多一次重试，其他错误直接失败；客户端得到脱敏错误与 Trace ID。
14. **如何处理并发领取？**
    UPDATE ... WHERE status=queued 的原子条件更新检查 rowcount，只有成功领取者执行。
15. **取消是立即的吗？**
    容器等待循环检查取消并删除容器；正在进行的模型请求需要等它返回或超时，不是硬实时取消。
16. **worker 被 kill 会怎样？**
    可能残留 running 和容器。V1 没有租约恢复/孤儿回收，需运维清理和 Owner 取消，不能描述为生产级队列。
17. **测试替身有什么价值，不能证明什么？**
    能确定失败分支、权限边界和状态转换；不能证明模型智能、真实 runsc 隔离或真实自动修复成功。
18. **下一步最值得做什么？**
    已完成小型已知 Bug 验收，下一步补崩溃恢复、成本控制与多样真实任务质量评测。

## 实现与未实现

真实代码已实现：LLM HTTP 协议、查询工具、鉴权、审批、持久任务、原子领取、过滤 worktree、
runsc 容器调用、受限编辑、测试证据判断、Diff、审核记录和 deterministic pytest。

已验收：真实 provider + runsc 下小型加法 Bug 的完整流程。未实现：自动应用 patch、自动 commit/push、
分布式调度、崩溃自动恢复、回归测试生成、任意语言工具链、模型质量统计。
